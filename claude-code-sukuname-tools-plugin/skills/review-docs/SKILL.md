# review-docs スキル

Markdown を書いたり変更したりしたあとに点検する。

書く前に規約を覚えるのではなく、**書いたものを見て直す**。規約は読んでも
守り漏らすが、出力を見れば違反は目に入る。

## 手順

1. 記法を検証する

   ```bash
   <skills>/review-docs/scripts/lint-md.sh <ファイル>
   ```

   複数ファイルや glob パターンを指定できる。**リポジトリの直下から実行する**。
   別のディレクトリから呼ぶと `.markdownlint-cli2.jsonc` が読まれず、
   緩和したはずのルールで落ちる。

2. 表現ルールに従っているかを目で確かめる

3. 他の文書と食い違っていないかを点検する

   ```bash
   <skills>/review-docs/scripts/list-docs.sh --grep <主題>
   ```

   パスと、h1 または `概要` の先頭行が 1 行 1 件で出る。**同じ主題を扱う
   文書を並べて読み、記述がずれていないかを見る。** 全件でも数十行なので、
   絞らずに眺めてもよい。

   変更した内容が他の文書にも書かれていた場合、片方だけ直すと食い違いが残る。

4. 規範を書き写していないかを確かめる

   規範の正は ADR にある。ドキュメントはそのビューであり、判断の理由や
   適用の条件は ADR へのリンクで簡潔に済ませる。詳しくは
   `repository-overview-0002` を参照。

   ADR を指すときは、ファイル名ではなく `id` を書く。

5. 違反や食い違いを直し、ユーザーへ結果を伝える

## markdownlint ルール

`.markdownlint-cli2.jsonc` を参照

- `gitignore: true` : .gitignore と同じ除外
- `MD041: false` : 先頭 h1 チェック無効（スキル等で @ 参照を使うため）
- `MD024: siblings_only` : 親見出しが異なる場合は同名の見出しを許可
- 既定では空白を含まない長い行 (パスや URL) は報告されない。ルールを
  無視するコメントを入れる前に、短く書けないかを検討する

  ```markdown
  <!-- markdownlint-disable MD013 -->
  長いコマンド例...
  <!-- markdownlint-enable MD013 -->
  ```

## 表現ルール

- 情報はリスト(箇条書き・番号付き)を積極的に採用して整理する
- リスト項目の末尾には句点を付けない
- 記号は原則半角にする(かっこ・セミコロンなど)
  - ただし句読点(、。)・中点(・)・波ダッシュ(〜)は全角を使う
- 数字は必ず半角にする
- 半角英数字・記号と全角文字の間には半角スペースを入れる(例: `Go 言語`)
  - ただし句読点の直後は不要(例: `実装する。Go で〜`)
- ユビキタス言語に従う (`docs-obsidian-vault/repository-overview/ubiquitous-language.md` を参照)
  - 定義済み用語は日本語表記を優先し、英語表記はコード上の識別子など必要な場面でのみ使う
  - 定義と異なる意味で用語を使わない

## 書くときに気をつけること

点検で拾える前提だが、次の 2 つは書く時点で意識すると手戻りが減る。

- 不明点は想像で補完せず、ユーザーに確認する
- 最小限から始めて、フィードバックを受けて足していく
