# record-adr スキル

判断を ADR (All Decision Record) として制定する。

書式と規則の正は
`docs-obsidian-vault/repository-overview/decisions/repository-overview-0001-record-decisions-as-adr.md`
にある。本スキルは手順だけを持つ。**着手前に必ずこの ADR を読むこと。**

## 手順

1. 上記の ADR を読み、書式と規則を確認する
2. `find-adr` skill で既存の ADR を検索し、同じ課題を扱うものがないか
   確認する

3. 新規作成か更新かを決める
   - 同じ課題を扱う ADR がある → **更新**
   - 無い → **新規作成**
4. 該当する手順へ進む

## 新規作成の手順

1. 粒度を決める

   「何に困ったのかという課題感が同一か」で判断する。困りごとが同じなら
   1 本にまとめ、違うなら分ける。ある決定を成立させるための下位の判断は、
   独立した課題ではないので同じ ADR に含める。

2. 置き場所を決める

   決定の主語がどこかで決まる。複数のプロジェクトにまたがる場合や、
   リポジトリの運営そのものが主語の場合は `repository-overview` に置く。

3. 階層を決める

   「どちらを選んでも上位の方針を達成できるか」で判定する。できるなら
   `choice`、できないなら `design` か `policy` になる。

4. ID を採番する

   ```bash
   <skills>/find-adr/scripts/list-adr.sh --dir <置き場所>
   ```

   既存の最大番号に 1 を足す。接頭辞は `decisions/` の親ディレクトリ名。

   並行して作業しているブランチがあると、同じ番号を採ることがある。
   マージ時に衝突したら、片方をリネームして `id` と参照を直す。

5. ファイルを作成し、6 節すべてを埋める

   節ごとに何を書くかは ADR の `決定事項 > 書式` に定義されている。
   埋まらない節がある場合は、粒度か対象の切り方を見直す。

6. 検証する

## 更新の手順

1. `version` の上げ幅を決める
   - `major` : 決定内容が変わり、従うべき内容が変わった
   - `minor` : 決定は変えずに情報を足した
   - `patch` : 表現だけを直した
2. frontmatter の `version` と `updated` を更新する
3. `変更履歴` に `v<version> (<日付>): <変更理由>` を 1 行追加する
4. `決定事項` に項目を足した場合は、その判断で比べた案を `却下事項` にも
   足す。決定だけを書いて却下理由を書き忘れるのが最も起きやすい抜けである
5. **用語・節名・値を変えた場合は、変更前の語で文書全体を検索し、
   取り残しを潰す**

   ```bash
   grep -n "<変更前の語>" <ADR ファイル>
   ```

   この取り残しは検証スクリプトでは検出できない。ADR を可変にしたことの
   代償なので、変更のたびに必ず実行する。

6. 検証する

## 検証

### 機械的な検証

```bash
<skills>/record-adr/scripts/check-adr.sh <ADR ファイル>
<skills>/write-document/scripts/lint-md.sh <ADR ファイル>
```

`check-adr.sh` は frontmatter・ID・ファイル名・節構成を検証する。
内容の妥当性は判定しない。

### 目視で確認すること

- `決定事項` に理由が混ざっていないか
- `決定事項` の各項目について、他の案と比べたのであれば、その案が
  `却下事項` に書かれているか。**決定を後から足したときに抜けやすい**
- `却下事項` の各項目に、その案の利点と却下理由の両方があるか
- `前提と見直し条件` の見直し条件が、程度の判断ではなく起きたと分かる
  事象になっているか
- 同じ内容を 2 箇所に書いていないか
