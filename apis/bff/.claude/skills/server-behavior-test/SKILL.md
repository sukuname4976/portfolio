# server-behavior-test スキル

サーバーの動作確認を対話的に行う。

## ステップ概要

1. サーバー起動を促す - AI: 起動コマンドを案内 / 人間: サーバーを起動して報告
2. ヘルスチェック - AI: curl 実行して確認
3. 動作確認の提案・ヒアリング - AI: 確認対象を提案 / 人間: 確認範囲を指示
4. テストケースの提案 - AI: テストケースを作成 / 人間: 内容を承認
5. テスト実行 - AI: curl 実行
6. レポート出力 - AI: 結果をまとめて出力

## ステップ詳細

### ステップ1: サーバー起動を促す

**AIのアクション:**

起動コマンドを案内する。

```bash
# 開発モード（ホットリロード）
make dev

# または本番同等のバイナリ
make build && make up
```

**人間のアクション:**

サーバーを起動し、「起動した」と報告する。

### ステップ2: ヘルスチェック

**AIのアクション:**

サーバーが起動しているか確認する。

```bash
curl -s http://localhost:8080/health
```

失敗した場合はユーザーに状況を確認する。

### ステップ3: 動作確認の提案・ヒアリング

**AIのアクション:**

以下の情報源から動作確認の対象を特定し、提案する。

- 現在の会話の文脈（直前の実装内容など）
- git diff や git status の変更内容
- OpenAPI 定義（IF/paths/, IF/components/）

提案例：

- 「echo エンドポイントの動作確認でよいですか？」
- 「どの程度網羅的に確認しますか？（正常系のみ / エラー系含む / 全パターン）」

**人間のアクション:**

確認したい対象と範囲を指示する。

例：

- 「echo エンドポイントを網羅的に確認したい」
- 「正常系だけでOK」

### ステップ4: テストケースの提案

**AIのアクション:**

ユーザーの要望に基づいてテストケースを作成し、提案する。

提案形式（箇条書き）:

```markdown
## テストケース

### 1. 正常系: <ケース名>

- 目的: <何を確認したいか>
- 検証内容: <どのフィールド・ステータスを見るか>
- 期待結果: <想定するレスポンス>
- コマンド:
  curl -X <METHOD> http://localhost:8080/api/v1/<endpoint> \
    -H "Content-Type: application/json" \
    -d '<request-body>'

### 2. 異常系: <ケース名>

- 目的: <何を確認したいか>
- 検証内容: <どのフィールド・ステータスを見るか>
- 期待結果: <想定するレスポンス>
- コマンド:
  curl -X <METHOD> http://localhost:8080/api/v1/<endpoint> \
    -H "Content-Type: application/json" \
    -d '<request-body>'
```

**人間のアクション:**

テストケースを確認し、承認または修正を依頼する。

例：

- 「OK、実行して」
- 「3番目のケースも追加して」

### ステップ5: テスト実行

**AIのアクション:**

承認されたテストケースの curl コマンドを実行し、結果を収集する。

### ステップ6: レポート出力

**AIのアクション:**

実行結果をまとめてレポートを出力する。

レポート形式:

```markdown
## 動作確認レポート

### 実行日時

YYYY-MM-DD HH:MM

### 対象

- エンドポイント: <METHOD> /api/v1/<endpoint>
- 確認範囲: <正常系 / 異常系 / 全パターン など>

### 結果サマリ

- 成功: X件
- 失敗: Y件

### 詳細

#### 1. 正常系: <ケース名>

- 結果: OK / NG
- ステータス: <期待したステータスコード>
- レスポンス: （実際のレスポンス）
- 備考: （あれば）

#### 2. 異常系: <ケース名>

- 結果: OK / NG
- ステータス: <期待したステータスコード>
- レスポンス: （実際のレスポンス）
- 備考: （あれば）
```

## 注意事項

- サーバーログも確認し、エラーログが適切に出力されているかも検証する
- 内部エラー詳細がレスポンスに漏れていないか確認する
- テスト実行前に必ずユーザーの承認を得る
