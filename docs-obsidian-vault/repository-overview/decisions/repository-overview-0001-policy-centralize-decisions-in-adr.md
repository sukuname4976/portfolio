# repository-overview-0001. あらゆる意思決定を ADR に集約し ADR を SSOT とする

## 決定事項

### 目的

- AI コーディングエージェントとの協働を安定させ、速くすることを目的とする
- あらゆる意思決定を ADR に集約し、ADR を規範の正とする

### 記録方式

- 決定は、判断ごとに独立した Markdown ファイル (ADR) として記録する
- コミットメッセージや PR 本文にも経緯は残るが、それらは記録の場所として
  扱わない
- 判断を伴う実装では、コードと同じ PR に ADR を含める

### 対象

- ADR の A は Architecture ではなく All として扱う。設計に限らず、
  プロダクト・運用・コードレベルを問わず、あらゆる決定を対象とする
- 記録する条件は「選択肢を実際に比べて片方を捨てたこと」とする。
  対象領域は限定しないが、比較のない決定は記録しない
- 人間が全件を読むことは想定せず、ファイル名と検索で辿る

### 置き場所

- リポジトリ全体に効く決定は
  `docs-obsidian-vault/repository-overview/decisions/` に置く
- それ以外は、nx プロジェクトに対応する
  `docs-obsidian-vault/projects/<プロジェクト>/decisions/` に置く

### ID とファイル名

- 接頭辞は `decisions/` の親ディレクトリ名をそのまま使う
  (例: `infra-terraform-0001`、`repository-overview-0001`)
- 連番はディレクトリごとに 1 から振り、4 桁で表記する
- ファイル名は `<id>-<level>-<決定内容を表す英語の kebab-case>.md` とする
- h1 の見出しは `<id>. <1 行の要約>` とする

### 位置づけと維持

- 規範の正は ADR とする。README や `agents-base.md` はその上に張るビューで
  あり、内容が矛盾した場合は ADR に従う
- 既存ドキュメントが本文として持つ規範は ADR へ移し、元の場所には参照と
  短い説明だけを残す
- ADR は書き換えてよい
- ADR 同士を矛盾させない。既存の方針を曲げる必要が生じた場合は、
  別の ADR で覆さず、該当する ADR 自体を書き換えて例外を本文に取り込む
- 制約のもとで妥協した内容も、それ自体が決定である。制約は
  `前提と見直し条件` に書き、制約が解消したときに何をするかもそこに書く
- 1 つの ADR にまとめる単位は「何に困ったのかという課題感が同一か」で判断する

### 階層

- `level` に、その決定がどの階層のものかを持つ。上位から順に
  `policy` → `design` → `choice` とする
  - `policy` : 何を作るか、どんな開発にするか
  - `design` : どんな方法で作るか、どう開発を仕組み化するか
  - `choice` : 細かい取捨選択。どちらを選んでも上位の方針は達成できるが、
    保守性のために判断が要るもの
- 判定は「どちらを選んでも上位の方針を達成できるか」で行う。できるなら
  `choice`、できないなら上の階層になる
- 1 本が複数の階層にまたがる場合は、主眼を置いた階層を書く

### 書式

- frontmatter に `id`、`summary`、`status`、`level`、`created`、`updated`、
  `version` を持つ
- `summary` は 200 字程度の人間向けの説明とする。本文ではなく frontmatter に
  置くことで、本文をすべて規範に保つ。日本語に不要な空白が混入しないよう、
  折り返しは `|-` を使う
- 本文は次の 6 節で構成し、すべて必須とする。任意の節は設けない。
  節は、書き先に迷わず、すべて埋めれば決定として成立するように定める
  - `決定事項` : 何をどうすると決めたかを、従える形の断定で書く。
    そう決めた理由はここに書かず、`コンテキスト` と `却下事項` で表す。
    項目が多ければ小見出しで整理してよい
  - `コンテキスト` : 何が起きていて、なぜ決める必要が生じたかを書く。
    決定した時点の事実だけを書き、評価や結論は書かない
  - `却下事項` : 案ごとに、その案なら得られたはずの利点と、却下した理由の
    両方を書く。捨てた利点がこの決定で引き受けたコストにあたり、
    却下理由がそのまま採用した案の長所にあたる
  - `前提と見直し条件` : 前提としたことと、それがどう変わったら何を
    見直すかを対にして書く。見直し条件は程度の判断を挟まず、
    起きたかどうかが一目で分かる事象として書く
  - `関連資料` : 参照した資料や関連する ADR を、この決定との関係を添えて
    書く
  - `変更履歴` : `v<version> (<日付>): <変更理由>` の形式で 1 行ずつ書く
- 採用した案は `決定事項` にのみ書き、`却下事項` には捨てた案と理由だけを
  書く。項目が増えたら小見出しで整理してよい
- 1 つの ADR の中で矛盾・重複・表記揺れを残さず、同じことは 1 箇所にだけ
  書き、用語や節名を変えたときは文書全体を見直す
- 他の ADR が扱う内容は本文に書かず、その ADR へリンクする。書き写すと
  一方を変えたときにずれ、後から消して回る作業が発生する
- ADR 間のリンクは、後から作られた ADR から先に作られた ADR へ向ける。
  逆向きのリンクは張らない。先に作られた側からはバックリンクで辿る
- ステータスは決定が生きているかどうかだけを表し、次の 2 値とする
  - `採用` : 現在有効な決定
  - `廃止` : 取り下げた決定
- `version` は `<major>.<minor>.<patch>` の 3 つの数字で表記し、初版を
  `1.0.0` とする。`1.0` のように 2 つで書くと YAML が数値として解釈するため、
  必ず 3 つ書く
- 内容を変更したら、次の基準で `version` を上げ、`updated` を更新し、
  `変更履歴` に理由を 1 行残す
  - `major` : 決定内容が変わり、従うべき内容が変わったとき
  - `minor` : 決定は変えずに情報を足したとき (却下事項への案の追加など)
  - `patch` : 表現だけを直したとき (誤字、言い回し、整形)
- `version` は 1 つの PR につき 1 回だけ上げる。同じ PR の中で何度書き換えても
  1 つの版にまとめ、`変更履歴` も 1 行に収める

## コンテキスト

このリポジトリは AI コーディングエージェントを実装の主体として開発している。
エージェントはタスクごとに文脈を持たずに着手するため、過去に何を決めたかを
知らないまま作業を始める。

Issue #9 の作業で行った判断について、根拠の所在は次の 4 箇所に分かれた。

- `terraform workspace` を採らず env ディレクトリ方式にした理由 → Issue #33
  のコメント
- `make check` を検証の単一の真実にした理由 → コミットメッセージ
- `terraform plan` を CI に入れない理由 → PR 本文の備考
- apply を人間が実行する理由 → README と `agents-base.md`

Issue のコメントとコミットメッセージは、トピックから引くことができない。
とくに Issue は閉じた時点で到達しづらくなる。

この状態では、既に比較して捨てた案が再び提案され、同じ検討をやり直すことに
なる。人間は毎回同じ説明を繰り返す。複数のエージェントが並行して動く場合は、
同じ問いに別々の答えを出す。協働が不安定になり、かつ遅くなる。

解き直しは設計の判断に限らず起きる。運用手順やツールの扱い方についての
判断でも、比較が残っていなければ、次に同じ場所を触る者が同じ検討から
やり直すことになる。

## 却下事項

### 記録方式

- **既存ドキュメントに「検討した代替案」節を足す**: 新しい仕組みが
  不要で軽いが、実装前の決定を書く場所がない。対応するドキュメントがまだ
  存在しないため
- **コミットメッセージと PR に残す現状維持**: 追加コストがないが、
  トピックから引けない。上記の散逸がまさにこの方式の結果である
- **却下した案を独立した ADR として切り出す**: 採用側の本文が短く
  なるが、却下案は決定ではないため種類の違うものが同じ棚に混ざる。
  却下理由は採用理由と表裏一体で、分離するとリンクを辿らないと
  解き直しを防げない。採用側が変わっても却下側は更新されず腐る

### 対象

- **対象を設計判断に限る**: 件数を抑えられるが、運用やコードレベルの
  判断でも解き直しは起きるため、防ぎたい問題の一部しか防げない

### 置き場所

- **`decisions/` をリポジトリ直下にフラットに置く**: 配置に迷わない
  が、API 仕様などプロジェクト固有の資料と同じ階層に混ざる。件数が増えた
  ときに破綻する

### ID とファイル名

- **接頭辞にディレクトリ名と異なる通称を使う**: ID が短くなるが、
  ディレクトリ名・nx プロジェクト名との対応表が必要になる。
  この 3 つは既に揺れているため、対応表は必ず腐る
- **番号を振らず説明的なファイル名だけにする**: 改番が発生せず
  リンクも読みやすいが、対話の中で決定を短く指し示せない

### 位置づけと維持

- **README を正とし ADR は参照専用にする**: 既存の運用を変えずに
  済むが、規範が複数箇所に本文として存在し、二重管理になる。矛盾したときに
  どちらへ従うかも決まらない
- **ADR を不変とし、変更時は新しい ADR で置き換える**: 過去の文言と却下理由
  がそのまま残り、外部からの参照も意味が変わらず、書き捨てにできるため
  保守債務が生じない。しかし決定の一部だけを変えるとき、現在の規範が複数の
  ADR に分散し、読み手が合成しなければならない。例外を本文へ取り込むことも
  できないため、矛盾を許さない運用が成立しない
- **ステータスを 4 値にする**: 「承認済み・置き換え済み・非推奨・棄却」は
  チーム開発で使われる区分だが、「承認済み」は承認者がいる前提の語であり、
  「棄却」は採用しなかった案が却下事項に入る本方式では発生しない。
  「置き換え済み」も、方針が変わったときは該当する ADR 自体を書き換えるため
  発生しない。「非推奨」は書き換えを許すため本文で表現できる
- **ADR 同士の優先順位を定め、逸脱を宣言した ADR を認める**: 制約下の
  妥協を原則と分けて書けるが、採用状態の ADR が互いに矛盾しうるため、
  1 つ読んでも従うべき内容が確定しない。逸脱の有無を毎回探す必要が生じ、
  ADR を正とした意味が失われる
- **ステータスに「暫定」を追加する**: 妥協であることを一目で示せるが、
  他の 2 値がライフサイクルを表すのに対し、これは確からしさを表しており
  軸が異なる。「暫定だが有効」と「暫定のまま廃止された」を区別できない
- **ADR 間のリンクを前後どちらの向きにも張る**: どちらから読んでも辿れるが、
  ADR を追加するたびに既存の ADR を編集することになり、変更が広がる。
  先に作られた側からはバックリンクで辿れる
- **書き換えのたびに `version` を上げる**: 変更の単位を細かく追えるが、
  1 つの PR で版が何度も飛び、レビューした版と最終的な版がずれる
- **`version` を単一の整数とし、表現の修正では上げない**: 変更履歴が
  意味のある変更だけになるが、`version` を見ても規範が変わっていないことを
  確認できない。3 段階にすれば `patch` が「規範は変わっていない」ことを
  積極的に伝えられ、`major` だけを追えば決定の変遷も辿れる

### 階層

- **階層を表すタグを設けない**: frontmatter が増えず判定の手間もないが、
  一覧を階層で絞れず、変更したときにどこまで波及するかも読み取れない
- **影響範囲を `全員` と `一部` の 2 値で持つ**: 二択なので判定が速いが、
  影響範囲と読む必要性を混同しており、判定が読み手のタスクに依存して
  揺れる。階層の情報も落ちる
- **階層をライフサイクル (仕様・設計・実装) で分ける**: 工程が読み取れるが、
  これは工程の順序であって深さの順序ではない。他のあらゆる決定を規定する
  決定が、どの工程にも収まらない
- **階層を「覆すと何が無効になるか」で分ける**: 依存の数で判定できるが、
  重要度と深さが乖離したときに直感と合わず、書き手が迷う

### 書式

- **「未確定事項」の節を設ける**: 決めきれていないことを書けるが、
  他の節が過去についての事実であるのに対し、この節だけが現時点の状態を
  写したものになる。後で確定しても消しに戻る動機がなく、決定済みの内容が
  未確定として残り続ける。作業項目は Issue へ、条件付きで再検討するものは
  前提と見直し条件へ振る
- **節に必須と任意の区分を設ける**: 書くことがない節を省けるが、
  区分に値する任意の節が「関連資料」だけになり、区分を維持する意味が
  無くなった。外部資料がなければ ADR 間のリンクを書けば埋まる
- **人間向けの要約を本文の「概要」節に置く**: 開いてすぐ読めるが、
  本文に規範でない節が混ざり、節ごとに規範か参考かの判定が必要になる。
  frontmatter へ置けば本文をすべて規範に保てる
- **`summary` の折り返しに `>-` を使う**: YAML の標準的な折り返し
  記法だが、改行が半角空白に変換されるため、日本語の文中に不要な空白が
  混入する。`|-` なら改行がそのまま残り、消費側で除去できる
- **「影響範囲」の節を設ける**: 決定の波及先を一覧できるが、対象スコープは
  ADR の置き場所が既に表しており、変更したファイルは git が持ち、実装済みか
  どうかは時間とともに古くなる。残るのは他の節に属する内容だけになる。
  トレードオフを直視させる役割は `却下事項` が、壊れる条件は
  `前提と見直し条件` が担う
- **書式と手順を別のドキュメントへ分離する**: ADR を判断だけに保てる
  が、書式は比較して決めた結果そのものであり、分離すると ADR を言い換えた
  だけのビューが増えて腐る。実行手順のみ skill が持つ
- **「理由」の節を設ける**: なぜこの案を選んだのかが 1 箇所で読めるが、
  却下理由と鏡像の関係になり、同じ内容を肯定形と否定形で二重に持つことに
  なる。一方だけを直したときにずれる
- **節を「比較検討」とし、採用した案も判定付きで併記する**: 何と何を比べた
  かが 1 箇所で読めるが、採用案が `決定事項` と重複し、書き換えたときに
  ずれる。また「検討したが保留」のような中間状態が紛れ込む余地が残る。
  採用した案は `決定事項` から読めるため、併記しなくても失われない

## 前提と見直し条件

- AI コーディングエージェントが実装の主体であることを前提とする。
  人間が主体の開発に戻ったとき、記録の粒度と量を見直す
- ソロ開発であることを前提とする。自分以外のコミッターが加わったとき、
  承認に相当するステータスとレビュー要件の要否を見直す
- エージェントが `agents-base.md` の指示に従って `decisions/` を検索する
  ことを前提とする。ADR はコンテキストへ自動で読み込まれず、件数の都合で
  全件を列挙することもできない。却下事項に記録済みの案をエージェントが
  再び提案したとき、参照のさせ方を見直す
- 書き換え可能にしたため、ADR は全件が保守の対象になる。決定を変更した際に
  同じ内容を書いた他の箇所の書き換え漏れが起きたとき、不変方式への移行を
  検討する。移行する場合は、置き換えの連鎖を辿る仕組みが別途必要になる
- 書き換え可能であることを前提に、ステータスを 2 値に絞っている。
  同じ規範について新旧の方式がプロジェクト間で並存したとき、
  ステータスへ「非推奨」を追加するかを見直す
- vault の `projects/` 配下が nx プロジェクトと 1 対 1 で対応していることを
  前提とする。nx プロジェクトの追加・分割・統合が起きたとき、置き場所を
  見直す
