# infra-terraform-0001. インフラを Terraform で管理し apply は人間が手動で行う

## 決定事項

### 管理の方針

- インフラの設定は Terraform でコードとして管理する。対象は特定のサービスに
  限定せず、IaC にできるものは最大限 IaC にする
- 状態を変える操作は Terraform に一本化する。コンソールや CLI から直接
  変更しない

### 適用の手順

- 変更をコミットしてから適用する。順序は次のとおりとする
  1. `terraform plan` で差分を確認する
  2. 変更をコミットする
  3. `terraform apply` で適用する
- `terraform apply` と `terraform destroy` は AI エージェントが実行しない。
  エージェントが進めてよいのは `terraform plan` までとする
- 人間が plan の差分を確認したうえで、手で実行する
- state はローカル管理とし、CI では適用しない

### 適用の担保

- 禁止は次の 2 層で担保する
  1. `.claude/settings.json` の `permissions.deny` に登録する
  2. `infras/terraform/README.md` と
     `docs-obsidian-vault/projects/infra-terraform/agents-base.md` に記載する
- `permissions.deny` のパターンは `*` を中間にも置き、
  `terraform * apply*` の形でオプションを挟む書き方も対象にする
- `permissions.deny` は最後の砦として扱い、一次的な歯止めは指示の側に置く

## コンテキスト

インフラの設定を画面から行うと、その情報はリポジトリの外に置かれる。
何をどう設定したかはコードにもレビューにも現れず、同じ状態を別の環境へ
作り直すこともできない。このリポジトリは、判断も設定も含めて情報を
リポジトリへ集める方針を採っている。

IaC のツールは複数あるが、Terraform が最も広く使われており、provider の
網羅性と参照できる情報の量で他を上回る。

適用の手順を決める必要が生じたのは Issue #9 である。GitHub リポジトリの
保護設定をコードにしたあと、適用の段階でエージェントが `terraform apply` を
実行しようとした。apply は設定を実際に書き換える操作で、ruleset の削除の
ように取り消しが利かないものを含む。当時それを止める仕組みは無く、実行する
かどうかはエージェントの判断だけに委ねられていた。

Claude Code の `permissions.deny` はコマンド文字列に対するグロブの一致で
判定する。`*` は先頭・中間・末尾のどこにでも置け、`&&` や `;` でつながった
複合コマンドは各サブコマンドが個別に判定される。一方で、引数を条件にする
パターンである以上、コマンド文字列を組み立て直す形には一致しない。

## 却下事項

### 管理の方針

- **画面から設定して手順書に残す**: 導入のコストがかからず、すぐ設定できるが、
  設定の実体がリポジトリの外に残る。誰がいつ何を変えたかを追えず、同じ状態を
  作り直すこともできない。手順書は実態とずれても気づけない
- **IaC を入れたうえで、コンソールや CLI からの変更も許す**: 急ぎのときに
  手早く直せるが、コードと実環境が乖離する。次の plan で意図しない差分として
  現れ、取り消すか取り込むかの判断が毎回発生する
- **Terraform 以外の IaC ツールを使う**: 言語や記述の好みで選べるが、
  利用者が少ないぶん provider の網羅性と参照できる情報の量で劣る。
  詰まったときに前例が見つからない

### 適用の手順

- **未コミットのまま適用する**: 手数が減り、試しながら進められるが、環境に
  だけ存在してコードに残らない変更が生まれる。現在の環境が何によって作られた
  のかを追えなくなり、コードを正とする前提が崩れる
- **AI エージェントにも適用を許可する**: 実装から適用まで一続きに進められ、
  人間の手が要らなくなるが、差分を人間が確認する工程が消える。取り消しの
  利かない変更が、誰も見ていない状態で入る
- **CI で自動的に適用する**: 適用の手作業が無くなり、実行者による差も
  出ないが、state をローカル管理しているため CI には state が無い。
  認証情報を CI へ置く必要も生じる

### 適用の担保

- **`permissions.deny` だけで担保する**: 設定 1 箇所で完結し、指示が守られ
  なくても止まるが、`sh -c "terraform apply"` や変数展開のようにコマンド
  文字列を組み立て直す形には一致せず、抜け道が残る
- **ドキュメントの指示だけで担保する**: 設定を触らずに済み、抜け道の議論も
  不要になるが、指示が読まれなかった場合に何も止めるものがない
- **`permissions.deny` を前方一致のパターンだけで書く**: 記述が短く済むが、
  `terraform -chdir=... apply` のようにサブコマンドの前にオプションを挟む
  書き方が素通りする

## 前提と見直し条件

- ソロ運用でレビュアーが本人のみであることを前提とする。自分以外の
  コミッターが加わったとき、適用を実行できる人の範囲を見直す
- state をローカル管理していることを前提とする。リモート state へ移行した
  とき、CI での適用を再検討する
- `permissions.deny` が Claude Code の設定として有効であることを前提とする。
  deny の記法や判定範囲が変わったとき、担保の方法を見直す
- Terraform が IaC ツールの中で最も広く使われていることを前提とする。
  他のツールが上回ったとき、移行するかを検討する
